# perf-sync

Performance harness that drives N realistic PouchDB clients against a live
CHT install, runs a chosen sync protocol (Nairobi `get-ids` vs the
Postgres-backed `/api/v1/pg-sync`), measures per-sync wall-clock timing, and
emits a CSV plus a stdout summary table.

This is Phase 1 of the harness — the core and the two simplest scenarios.
Heavy-upload, background-writes, and purge scenarios are picked up by
`perf-harness-scenarios` (Phase 2).

## Process model

The harness runs in a single Node process. Each virtual user is a
Promise; the runner spawns N of them with `Promise.all` and collects
metric rows into a shared buffer as they complete. Per-user state — the
in-memory PouchDB instance, the auth context, the protocol driver —
lives inside that Promise's closure. The sync workload is IO-bound
(HTTP + a small in-memory PouchDB), so a single event loop is the
natural fit; the earlier fork-per-user model paid a per-child startup
tax and a duplicated require graph for no measurable benefit.

## Test data is generated by `test-data-generator`

The harness does **not** roll its own contact / data_record / user
generator. Setup invokes the sibling [`test-data-generator`][tdg] repo
with the `perf-many-users` design — a thin wrapper around
`sample-designs/many-users.js` — that produces, per virtual user:

- A `district_hospital → health_center → household → {patients, chw}`
  subtree.
- A `chw-supervisor` sibling under the district hospital.
- For the CHW: a `_users` doc, a `user-settings` doc, telemetry, 100
  tasks, and one pregnancy-danger-sign report.

The wrapper overrides only the CHW's `username` field — every CHW gets
the deterministic name `perf-chw-<run-id>-<i>` so the harness can sign
in by index without round-tripping CouchDB. Everything else (place
shapes, person details, task generation, telemetry) comes straight from
upstream and is not re-implemented here.

[tdg]: https://github.com/medic/test-data-generator

## Prerequisites

- A reachable CHT install (the URL goes in `config.json`).
- Admin credentials in `config.json`. They get folded into a `COUCH_URL`
  env var that test-data-generator's writer reads.
- Node 22.x (matches CHT's engines field).
- `test-data-generator` checked out as a sibling of this repo and built:

  ```bash
  cd ../test-data-generator
  npm ci
  npm run build
  ```

  By default the harness probes
  `../../../../test-data-generator` (merged-into-openchis layout) and
  `../../../../../../test-data-generator` (running from a `.agents`
  worktree). Set `PERF_SYNC_TDG_PATH` to point elsewhere.

## Configuration

`config.json` (template ships in this directory):

```json
{
  "url": "http://localhost:5988",
  "admin": { "username": "medic", "password": "password" }
}
```

Override at the command line with `--config=path/to/config.json`.

## Invocation

```bash
node tests/perf-sync/cli.js --help

# baseline: each of N users does one initial sync.
node tests/perf-sync/cli.js baseline --users=50 --protocol=both

# initial-vs-ongoing: warm a fraction up, then a second-round sync across all.
node tests/perf-sync/cli.js initial-vs-ongoing --users=50 --warmed-fraction=0.8 --protocol=both
```

`--protocol` accepts `nairobi`, `pg-sync` (alias `pg`/`postgres`), or `both`.

`--run-id=<id>` (default: a timestamp) is baked into every CHW username.
Re-using the same `--run-id` reuses the same usernames — generally the
harness creates new docs without overwriting, so use a fresh run-id for
each pass.

## CSV output

Results are written to `tests/perf-sync/results/<scenario>-<protocol>-<ts>.csv`:

| column | meaning |
|---|---|
| `scenario` | scenario name (`baseline`, `initial-vs-ongoing`) |
| `protocol` | `nairobi` or `pg-sync` |
| `user_id` | the username of the virtual user |
| `sync_index` | 0-based sync within the user's scenario flow |
| `kind` | `initial` or `ongoing` |
| `docs_pulled` | docs the client received from the server this sync |
| `docs_pushed` | always 0 in Phase 1 (uploads are Phase 2) |
| `elapsed_ms` | wall-clock around the sync call |
| `error` | empty on success, error message on failure |

A stdout summary follows the run:

```
scenario=baseline protocol=nairobi users=50
  p50=820ms  p95=2410ms  p99=4180ms  throughput=12.1/s  errors=0
scenario=baseline protocol=pg-sync users=50
  p50=180ms  p95=420ms   p99=510ms   throughput=58.3/s  errors=0
```

## Cleanup

**The harness does not delete anything it creates.** CouchDB DELETE
leaves tombstones that participate in views, replication, and changes
feeds forever — for a perf tool that writes thousands of docs per run,
auto-cleanup would pollute every subsequent measurement.

Each run's `--run-id` is the cleanup hook: the CHWs it creates are named
`perf-chw-<run-id>-<i>`, easy to identify by prefix. Re-running with a
new `--run-id` (default: a timestamp) gives every run its own
namespace; old runs become inert.

If you need a clean database between long-running campaigns, drop and
re-create `medic` yourself.

## Tests

The harness binary is end-to-end against a live deployment, but its
library pieces are unit-tested with mocks:

```bash
npx mocha 'tests/perf-sync/test/**/*.spec.js'
```

The unit tests must run without a live CHT, Postgres, or
`test-data-generator` writes — they use `pouchdb-adapter-memory` for
in-process PouchDB and `sinon` stubs for `fetch`, `Docs.createDocs`,
and `PouchDB.replicate`.
